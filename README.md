# MarketingMixer

**MarketingMixer** - демо клиент-серверного приложения для прогнозирования маркетинговых инвестиций. Целевой продукт должен объединить разрозненные калькуляторы в единый интерфейс на **Next.js + React + TypeScript**, где собственник, CMO или CFO может быстро оценить сценарии роста, риски и распределение бюджета без штатного эконометриста.

Первая версия в этом репозитории должна быть облегченной демо-версией для **GitHub Pages**. На этом этапе приложение работает как интерактивный клиентский прогнозатор: расчетная логика выполняется на клиенте, данные не сохраняются в production-хранилище, а серверные функции имитируются или откладываются до Vercel/server-side этапа.

## Контекст

Изначальное ТЗ описывает MarketingMixer как независимого советника по планированию маркетинговых инвестиций: продукт не продает рекламные каналы, а помогает понять, куда направить бюджет, где риск слишком высок и какой результат в деньгах можно ожидать на горизонте 1-3 месяцев.

Главная работа продукта:

> Когда у меня падают продажи или я хочу вырасти, мне нужно быстро понять, что именно сделать в рекламе и продвижении, чтобы это дало измеримый результат, без изучения маркетинга и риска потратить бюджет вслепую.

Для демо это переводится в более узкую задачу: собрать существующие калькуляторы в единый dashboard, показать прогноз атрибутированной выручки, бюджета и ROMI, а также дать пользователю путь к уточнению модели через собственные ретро-данные и управляемые веса факторов.

## Принятые решения

### Продукт и демонстрация

- Главный демо-сценарий: **общий media mix** с возможностью углубиться в маркетплейсы, eGrocery и другие digital/retail инструменты.
- Первые зрители: **потенциальный клиент** и **инвестор**.
- В демо нужен простой логин: `demo / Demo.2026`. Это не production auth, а контролируемый вход в демонстрационный сценарий.
- Три главные метрики первого экрана: **атрибутированная выручка**, **бюджет**, **ROMI**.
- Вместо пассивного дисклеймера нужен активный сценарий **"Уточнить"**: пользователь может загрузить ретро-данные в нужном формате и задать рамку весов для факторов вне доступного мониторинга.

### Данные и методология

- Допустимые источники для стартовых бенчмарков: АКАР, Data Insight, отчеты площадок, собственные интервью, экспертные оценки.
- Если несколько источников влияют на один показатель, в демо можно усреднять значения и явно показывать это усреднение.
- В демо все коэффициенты считаются гипотезами и результатом наблюдений, а не доказанной универсальной нормой.
- В production рядом с каждым коэффициентом нужна версия источника. В демо достаточно общего документа: какие источники используются для каких метрик.
- Неопределенность показывается через **диапазоны результата** и **confidence score**.

### Техническая реализация

- Основной целевой стек остается Next.js + React + TypeScript, но допустим промежуточный этап стабилизации Vite.
- Репозиторий для GitHub Pages: `https://github.com/kirillchistov/marketingmixer.git`; ожидаемый `basePath` для project site: `/marketingmixer`.
- В демо фокус на одном основном калькуляторе, остальные сохраняются и размещаются на вкладках как дополнительные сценарии.
- Библиотека графиков: начать с **Recharts** как React-friendly варианта, но архитектуру графиков держать заменяемой. Для приближения к возможностям PowerBI могут понадобиться разные библиотеки, включая amCharts или специализированные визуализации.
- Базовые тесты расчетов нужны уже на первом этапе, минимум для отсечения заведомо абсурдных результатов.

### Путь к клиент-серверной версии

- Первый production-хостинг после демо: **Vercel**, далее возможен собственный VPS.
- Первая критичная интеграция: **Яндекс.Метрика** для сценария компаний, по которым мало данных.
- Первыми сохраняются **сценарии расчетов**.
- Авторизация: на демо простейшая, далее собственная авторизация с JWT, OTP и Яндекс OAuth.
- Для LLM нужен прототип соглашения об использовании: пользователь явно принимает, что сервис может использовать LLM для построения прогнозов.

## Цель первой демо-версии

Сделать демонстрационное приложение, которое можно открыть на GitHub Pages и за 5-10 минут показать:

- как пользователь выбирает цель, период и стартовые параметры бизнеса;
- как система строит общий media mix по каналам;
- как можно углубиться в маркетплейсы, eGrocery и retail/digital инструменты;
- какую атрибутированную выручку, бюджет и ROMI показывает модель;
- как меняется результат при разных диапазонах неопределенности;
- как работает сценарий **"Уточнить"** через загрузку ретро-данных и настройку весов внешних факторов;
- какие данные нужно подключить в будущей серверной версии для повышения точности.

Демо не должно прятать приблизительность расчетов, но и не должно начинаться с пугающего дисклеймера. Правильная механика доверия: показать текущую оценку, уровень уверенности и конкретный способ улучшить прогноз.

## Основные пользовательские сценарии

### 1. Известный бренд

Для крупной компании или бренда, по которому уже есть публичные и накопленные данные:

- пользователь вводит название бренда;
- выбирает цель и период;
- опционально выбирает ключевых конкурентов;
- получает стартовый media mix forecast с диапазоном и confidence score.

### 2. Средняя компания с частично известным сегментом

Для компании, по которой есть сегментные данные, но нужна калибровка:

- пользователь вводит название компании/категорию, цель и период;
- отвечает на 2-3 калибрирующих вопроса: выручка за период, бюджет за период, текущий микс;
- получает прогноз и видит, какие показатели были взяты из бенчмарков.

### 3. Компания без достаточных данных

Для компании, по которой почти ничего не известно:

- пользователь проходит полноценный квиз;
- подтверждает наличие ретро-данных или готовность работать по отраслевым бенчмаркам;
- выбирает толерантность к высокой погрешности;
- получает первичный прогноз с низким/средним confidence score;
- видит, какие данные нужны для уточнения.

### 4. Уточнить прогноз

Сценарий **"Уточнить"** должен стать альтернативой обычному дисклеймеру:

- загрузить ретро-данные в согласованном формате;
- указать рамку весов для факторов вне мониторинга: дистрибуция, работа с медспециалистами, фронт/бэк-маржа, промо-давление, изменения цены, сезонность, операционные ограничения;
- увидеть, как меняются ROMI, атрибутированная выручка и confidence score;
- сохранить сценарий в будущей клиент-серверной версии.

## Scope: GitHub Pages Demo

### Входит в первую версию

- Главная страница с кратким позиционированием и демо-логином.
- Dashboard layout по мотивам `next-admin-dash`/shadcn admin dashboard: sidebar, верхняя панель, карточки метрик, формы, графики, темная/светлая тема.
- Основной модуль **Media Mix Forecaster**.
- Вкладки углубления: **Marketplaces**, **eGrocery**, позднее другие digital/retail инструменты.
- Первый экран результата: атрибутированная выручка, бюджет, ROMI.
- Диапазоны результата и confidence score.
- Сценарии **optimistic / realistic / pessimistic**.
- Сценарий **"Уточнить"** с описанием формата ретро-данных и весов внешних факторов.
- Панель **"Как это посчитано"**: формулы, коэффициенты, источники, усреднение источников, ограничения.
- Блок **"Качество данных"**: что ввел пользователь, что взято из бенчмарка, что является гипотезой модели.
- Экспорт результата в CSV или print-friendly view.
- Статическая сборка и деплой на GitHub Pages.

### Не входит в первую версию

- Реальные API routes и серверная бизнес-логика.
- Реальное сохранение сценариев в базе данных.
- OAuth-подключения к Яндекс.Метрике, Яндекс.Директ, VK Ads, CRM.
- Production-grade авторизация.
- Production-grade расчет MMM с атрибуцией по историческим данным.
- Реальные LLM-вызовы напрямую из GitHub Pages.

Ограничение важно: GitHub Pages не является Node.js-сервером. Для Next.js на GitHub Pages нужен static export, поэтому server actions, API routes и безопасное хранение LLM/API ключей переносятся на Vercel/server-side этап. В GitHub Pages демо можно показать прототип соглашения и mock/заготовку LLM-сценария, но не безопасный production-вызов LLM.

- PostgreSQL/Supabase или другой managed storage.

- Перенос критичных backend-компонентов на собственную инфраструктуру.

- История расчетов, сравнение сценариев, отчеты.

## Расчетная методология демо

Первый перенос должен сфокусироваться на общем media mix, а eGrocery и маркетплейсную юнит-экономику подключить как углубления.

Методология демо:

- стартовые коэффициенты являются гипотезами и наблюдениями;
- допустимо использовать АКАР, Data Insight, отчеты площадок, интервью и экспертные оценки;
- если несколько источников влияют на один показатель, расчет показывает усреднение;
- ключевые выходы: атрибутированная выручка, бюджет, ROMI, диапазон результата, confidence score;
- результат должен явно разделять факт, прогноз и предположение;
- каждый коэффициент в production должен иметь версию источника, а в демо - ссылку на общий документ источников.

Для вкладки eGrocery нужно сохранить уже реализованную логику:

- базовый ROAS по платформам;
- модификаторы категории FMCG;
- позиционирование бренда: economy / mid / premium;
- тип продукта: basic / ultra fresh / ready to eat;
- OSA, рейтинг, количество отзывов, индекс цены, глубина и частота промо;
- комиссии платформ;
- diminishing returns при чрезмерной доле бюджета;
- синергия внешних каналов с eGrocery платформами.

## Тесты расчетов

На первом этапе нужны базовые тесты, которые не доказывают точность модели, но защищают от абсурдных результатов:

- бюджет не может стать отрицательным;
- ROMI не должен становиться `NaN`, `Infinity` или уходить в невозможные значения из-за деления на ноль;
- сумма распределения бюджета нормализуется и объясняется пользователю;
- рост бюджета не должен автоматически давать бесконечный рост результата;
- confidence score должен снижаться при нехватке данных;
- сценарии optimistic / realistic / pessimistic должны иметь ожидаемый порядок результатов.

## UX-принципы

- Язык денег важнее маркетингового жаргона: сначала рубли, риски и действия, затем ROAS/ROI.
- Первый экран результата: атрибутированная выручка, бюджет, ROMI.
- Не больше 3 главных действий на экране.
- Не больше 5 ключевых метрик на первом экране результата.
- Любой прогноз показывается диапазоном и confidence score.
- Факт, прогноз и предположение визуально разделены.
- Вместо пассивного дисклеймера пользователь получает действие **"Уточнить"**.
- Если данных мало, продукт не блокирует пользователя, а объясняет цену неопределенности.
- Mobile-first: демо должно нормально работать на ноутбуке и смартфоне.

## Прототип соглашения об использовании LLM

В демо нужен текст соглашения и checkbox на входе/регистрации. Смысловая рамка:

- пользователь понимает, что сервис может использовать LLM для построения прогнозов, объяснений и рекомендаций;
- пользователь подтверждает, что не загружает данные, которые не имеет права передавать третьим сервисам;
- прогнозы являются аналитическими гипотезами, а не финансовой гарантией;
- в production должна быть отдельная политика обработки данных и список поставщиков LLM/API.

Важно: реальный LLM-вызов из статического GitHub Pages демо небезопасен из-за хранения ключей на клиенте. Для настоящего LLM нужен backend/proxy на Vercel или другом серверном окружении.

## План миграции

1. Сравнить `mediamix-optimizer/` и `src/app-data.js`, выбрать каноническую media mix модель.
2. Перенести media mix расчеты в чистые TypeScript-функции без DOM-зависимостей.
3. Добавить базовые тесты расчетов и ограничители абсурдных результатов.
4. Создать dashboard shell: логин `demo / Demo.2026`, overview, вкладки сценариев.
5. Собрать основной Media Mix Forecaster.
6. Добавить вкладки Marketplaces и eGrocery как углубления с текущими калькуляторами.
7. Добавить диапазоны, confidence score, source trace и блок качества данных.
8. Добавить сценарий **"Уточнить"**: формат ретро-данных, веса внешних факторов, пересчет.
9. Настроить GitHub Pages deploy для `/marketingmixer`.
10. После демо подготовить Vercel MVP: сохранение сценариев, Яндекс.Метрика, server-side LLM proxy.

## Deploy на GitHub Pages

Деплой описан в `.github/workflows/deploy-pages.yml`.

Workflow запускается при push в `main` или `master`, а также вручную через `workflow_dispatch`. Он выполняет:

1. `pnpm install --frozen-lockfile`
2. `pnpm test`
3. `pnpm build`
4. публикацию папки `out/` через официальный GitHub Pages artifact

Для работы URL `https://kirillchistov.github.io/marketingmixer/` в настройках репозитория нужно выбрать:

- `Settings -> Pages -> Build and deployment -> Source: GitHub Actions`
- затем запустить workflow `Deploy GitHub Pages` вручную или сделать push в `main`/`master`

Если Pages настроен на branch `gh-pages`, этот workflow не будет использоваться до переключения Source на `GitHub Actions`.

## Критерии готовности GitHub Pages Demo

- Приложение открывается по публичному GitHub Pages URL `https://kirillchistov.github.io/marketingmixer/`.
- Есть демо-логин `demo / Demo.2026`.
- Главный сценарий - общий media mix от ввода цели до результата.
- Первый экран показывает атрибутированную выручку, бюджет и ROMI.
- Есть вкладки Marketplaces и eGrocery как углубления.
- Расчетное ядро находится в TypeScript-модуле и не привязано к DOM.
- Есть базовые тесты расчетов против абсурдных результатов.
- Пользователь видит диапазон результата и confidence score.
- Есть сценарий **"Уточнить"** с ретро-данными и весами внешних факторов.
- На странице нет артефактов другого продукта (`Stindex`, inventory dashboard и т.п.).
- README честно разделяет: "статическое демо сейчас", "Vercel MVP дальше" и "собственный VPS позже".
